## §0 结论摘要

产品已经把最难的一段走完了：**链上可查的自动理赔闭环**（喂价 → 三模型验收 → AI 判定 → claim → 到账），并且有了骑手 H5、平台控制台、批量投保、预警停售、小时级喂价、多签治理与运营手册。所以现在的问题**不是"能不能跑"，而是"离真实业务还差什么"**。

最该补的三处洞（其余见 §2）：

1. **可验证性还缺最后一环**：链上能查"判定结果"，但查不到"原始数据与复算过程"。买家真正信的是"我自己能重算一遍"。→ G5/G6/G7。
2. **数据源是单点**：ECMWF / GFS / ICON 三个模型的名字看着是"三源",实际**同一家供应商（Open-Meteo）**。供应商挂了或口径变了，三模型一起歪。→ G4。
3. **绩效与体验在弱网/移动端会掉**：三个页面首屏各自要拉 `ethers.umd.min.js`（526 KB），加页面本身，未压缩首屏 ≈ 0.78 MB（目录文件 137 KB 另按需拉）；骑手在暴雨天的弱网上这是真实风险。→ G13/G14/G15。

## §2 增量改进项

> 编号 `G1–G20`；`★P0/★P1/★P2` 是建议优先级。每条给：现状证据 → 完善方向 → 产品价值 → 可行性 → 验收。

### A 组 · 功能、数据与可信（更"像保险"、更贴实际场景）

**G1 保单凭证（链上可查 + 可下载）★P0**
- 现状：投保后页面只显示状态，没有一张"保单"。`rider.html` 无凭证/导出逻辑。
- 方向：投保成功即生成凭证页（保单号=txHash+logIndex、城市、时段、保额、触发条件、数据源、条款哈希、核验入口 URL），支持"保存图片/复制链接"。
- 价值：骑手能截图发给站长/家人；平台能对账；评委一眼看到"这就是保单"。
- 可行性：纯前端 + 已有链上读；**1–2 天**。风险：无。
- 验收：任意一笔投保，用凭证里的链接在核验台能查到同一笔；离线（快照模式）也能显示静态凭证。

**G2 理赔流水与到账凭证 ★P0**
- 现状：赔付事件能查到，但没有"我的理赔记录"列表（含被拒原因）。
- 方向：`rider.html` 加"我的理赔"：每笔保单 → 判定结果（PAY/DENY）→ 原因（R1–R5 命中哪条）→ 金额 → 到账 txHash。
- 价值：**"不赔也要说清为什么不赔"**是本产品的说服力核心（真实不赔那笔就是最好的案例）。
- 可行性：读事件 + 已有判定留痕；**1 天**。
- 验收：真实不赔那笔（上海 34 mm < 50 mm）在列表里显示 DENY + 规则命中说明。

**G3 条款与免责（含哈希上链）★P1**
- 现状：无条款文本；免赔额、等待期、争议处理都没写。
- 方向：定稿一份 1 页条款（参数化：触发阈值、数据源、判定规则、到账时限、免责：数据源不可用/不可抗力/重复投保），在页面展示，并把**文本哈希**写进保单或留痕文件（合约不改，走留痕/事件旁路）。
- 价值：合规与信任的底线；B 端采购必问。
- 可行性：文档 + 前端展示 + 留痕哈希；**2–3 天**（合约不动，符合"A 已退出、不改已部署源码"的红线）。
- 验收：条款页可访问、哈希可复算、留痕里有对应记录。

**G4 第二数据供应商（异构源）★P0**
- 现状：三模型 ECMWF/GFS/ICON 全部经 **Open-Meteo** 取得（同源）。
- 方向：接第二家（如中国气象局公开接口/和风天气/WeatherAPI 等，选有免费额度且许可允许留痕的），在验收逻辑里做**跨源一致性检查**（不通过就不喂价，或降级为人工复核）。
- 价值：把"三模型验真"升级为"跨供应商验真"，直接消除单点风险；对外讲"三源"才站得住。
- 可行性：新增一个采集器 + 验收分支；**3–5 天**，依赖账号/额度。风险：许可条款（必须允许留痕与非商用/商用范围写清）。
- 验收：故意让一家返回异常值 → 系统拒收并记录"跨源不一致"。

**G5 原始报文留痕 + 哈希锚定 ★P0**
- 现状：留痕 JSON 存了模型读数，但没有把"原始响应"整体锚定（评委无法证明数据没被改）。
- 方向：每次喂价把三家原始响应（或规范化后的逐模型读数）打包 → SHA-256 → 写进留痕文件 + 作为喂价交易的附加字段（或独立 `note` 交易），并把文件放本地仓库/对象存储。
- 价值：**"数据没被改"从声明变成可复算事实**，这是产品的护城河。
- 可行性：脚本侧改造 + 留痕格式升级；**2–3 天**。风险：链上写 note 会产生额外交易成本（极小）。
- 验收：给第三方一个 `原始报文.json` → 能算出与链上一致的哈希。

**G6 一键重放器（可复算页面）★P1**
- 现状：核验台能查交易，不能复算判定。
- 方向：核验台加"重放"：输入留痕 JSON（或链上哈希）→ 页面内跑一遍 R1–R5 + 聚合 → 输出 outputHash 并与链上比对（纯前端、无后端）。
- 价值：**"你自己算一遍"**——把 AI 判定从黑箱变成可审计函数。
- 可行性：把判定规则移植为前端纯函数（规则已在留痕文件里固化）；**2–3 天**。风险：规则版本漂移 → 需把规则版本号写进留痕。
- 验收：拿真实那两笔（PAY/DENY）重放，哈希一致。

**G7 数据源健康档案与时效看板 ★P1**
- 现状：`notify.js` 有告警；无对外可见的"数据源历史表现"。
- 方向：每城每源的可用率/延迟/拒收次数/缺口统计 + 一张页面（可离线导出 PNG）。
- 价值：让"我们盯得住数据源"变得可见；也给 B 端 SLA 谈判留证据。
- 可行性：读留痕聚合成 JSON + 前端图表；**2 天**。
- 验收：能展示最近 N 天的拒收与延迟曲线。

**G8 保额/免赔/等待期的可选性 ★P2**
- 现状：保额与赔付档固定（PAYOUT_MAX、分档 50%/75%）。
- 方向：给骑手 2–3 档（低保费低赔/高保费高赔），或引入免赔额让价格更便宜。
- 价值：真实保险的定价自由度，能覆盖不同风险偏好。
- 可行性：**改合约**（v5 已是新部署，可在 v6 里做）；**1 周**。风险：需要重新校准精算与门禁。
- 验收：两档价格同时满足赔付率与池子约束。

**G9 申诉与复核通道 ★P1**
- 现状：无骑手端申诉入口。
- 方向：页面提供"申请复核"（填保单号 + 理由，产物是一封邮件/一条留痕记录），运营侧按手册处置并回填结论（链上不改，走留痕）。
- 价值：参数化产品也需要"人对人"的最后一层，B 端采购会问。
- 可行性：前端表单 + 本地留痕；**1 天**。
- 验收：一次申诉从提交到结论全程可在留痕文件里追溯。

**G10 平台侧对账与结算 ★P1**
- 现状：`console.html` 能生成计划、批量投保，但没有"本期平台补贴金额、已赔付、待赔付"的对账表。
- 方向：控制台加一个"结算视图"（导出 CSV）：名单、保费、赔付、净支出。
- 价值：平台方真正关心的不是链，而是**账**。
- 可行性：读事件 + CSV 导出；**1–2 天**。
- 验收：导出 CSV 与链上事件逐笔可对。

**G11 城市目录扩容与懒加载 ★P1**
- 现状：6 城（`v5-regions.json`），`cn-cities.json` 136,996 B 全量加载。
- 方向：把目录扩到可演示的 15–20 城（有历史雨量数据的），页面按需加载/裁剪目录。
- 价值：从"5 城示范"变成"能覆盖主要劳务输入地"。
- 可行性：数据采集 + 定价网格重算 + 门禁扩表；**3–5 天**。风险：新城市缺少历史数据 → 只能做同分布假设，需在材料里标注。
- 验收：新城市定价通过门禁与精算自检。

### B 组 · 性能与工程

**G12 每笔投保两笔交易 → 一笔 ★P0**
- 现状：`rider.html:288` 每笔投保都要 `approve` + 投保两笔交易（`batch-buy.js` 走一次性总额规避了这点）。
- 方向：ERC-2612 `permit`（离线签名授权）或"授权一次额度上限"引导；合约侧若要改则并入 v6（不改已部署 v5）。
- 价值：少一次签名与 gas，支付成功率明显提高（手机钱包体验差距最大的一环）。
- 可行性：前端为主（permit 需代币支持）；**1–2 天**（若代币支持 `permit`）；否则记入 v6。
- 验收：投保只用一笔交易完成；失败率对比。

**G13 首屏瘦身（去 UMD / 拆包）★P1**
- 现状：三页都加载 `ethers.umd.min.js`（526,551 B）+ 目录文件。
- 方向：① 只保留用到的 ABI 编解码（自写极简或按需 import）；② `cn-cities.json` 懒加载；③ 演示页按路由拆包。
- 价值：弱网首屏从 ~0.9 MB 降到 ≤0.3 MB，加载时间可感知地缩短。
- 可行性：前端改造（核验台单文件已证明"不用 ethers 也能验链"是可行的先例）；**2–3 天**。风险：读链路径多，需回归。
- 验收：首屏字节数达标 + 投保/查保单/查事件全流程回归通过。

**G14 轮询策略（可见性感知 + 退避）★P1**
- 现状：`rider.html:301` 固定 30 s；演示页 12 s；失败无退避。
- 方向：`document.hidden` 时暂停；失败后指数退避（最长 60–120 s）；成功后恢复。
- 价值：省电省流量，避免"错误横幅反复闪"这类观感事故。
- 可行性：**半天**。风险：无。
- 验收：切到后台不再发请求；断网恢复后自动重连。

**G15 RPC 探测缓存与并发竞速 ★P1**
- 现状：四层降级串行试错；677 直连 5,090 ms 超时。
- 方向：探测结果缓存（如 5 min）、并发竞速（首个成功即用）、首屏骨架屏。
- 价值：首屏等待从"最长一层超时"变成"最快一层返回"。
- 可行性：**1 天**。风险：并发请求会略微增加配额消耗。
- 验收：断掉首层时首屏仍在 2 s 内出内容。

**G16 偿付能力面板（把精算搬到台前）★P1**
- 现状：`10-金融与定价/reserve_mc.js` 有蒙特卡洛结果（固定种子），页面看不到。
- 方向：控制台/核验台加一屏：池子余额、在保敞口、历史赔付、模拟破产概率（不同承诺份数下的曲线）。
- 价值：把"我们能赔得起"变成可视化证据，对 B 端是硬参数。
- 可行性：读链上 + 复用既有蒙特卡洛输出；**2 天**。
- 验收：任一时刻池子水位与页面一致；曲线可重算（种子固定）。

**G17 资金流水台账 ★P1**
- 现状：注入/赔付/余额分散在交易里，无台账。
- 方向：一张表（时间、类型=注资/保费/赔付/提款、金额、txHash、余额快照），支持导出。
- 价值：运营第一需求；也是"没乱动钱"的自证。
- 可行性：读事件聚合；**1–2 天**。
- 验收：台账期末余额 == 链上 `balanceOf`。

**G18 门禁补两块（前端 e2e 与迁移演练）★P2**
- 现状：20 环节门禁覆盖合约/ABI/页面解码/定价/事件/语法；**不含浏览器交互**，也没有 v4→v5 迁移演练。
- 方向：加一条无头浏览器冒烟（打开三页 → 选城市 → 读到状态 → 不报错）；加一条本地链迁移演练（v4 现值 → v5 种子 → 断言关键状态）。
- 价值：防止"改了页面没人发现"和"迁移脚本只在一次手工操作里验证过"。
- 可行性：需要 Playwright/本地链依赖；**2–3 天**。风险：CI 已停（不 push），只在本地跑。
- 验收：故意改坏一个元素 → 门禁红。

**G19 本地定时替代 GitHub Actions ★P1**
- 现状：`.github/workflows/` 只有 gates/deploy 两个、无 cron；且约定不再 push ⇒ CI 已实际失效。
- 方向：本地定时方案（Windows 任务计划 → `04-脚本` 的喂价/监控/门禁脚本；或常驻 `--watch`），并把"每天跑一次门禁"写进运营手册。
- 价值：**不 push 不等于不自动**——把失去的自动化用本地方式补回来。
- 可行性：**半天**。风险：本机 sleep 时不执行 → 需在手册里写明补偿动作（昨日缺口补喂）。
- 验收：断电/休眠恢复后能看出哪些任务漏跑，并可一键补齐。

### C 组 · 可解释性与合规

**G20 判定可解释输出与 confidence 口径 ★P1**
- 现状：判定结果有 PAY/DENY，留痕里有三模型读数；`confidence` 是**模型自报值**（94/95 之类），不是可复算统计量。
- 方向：① 页面展示"为什么这么判"（命中规则 + 三模型读数 + 离群剔除记录）；② 把 confidence 改为可复算口径（如"三模型一致的比例 + 与历史同站点的偏离度"），或明确标注为"模型自评，非统计置信度"。
- 价值：避免把自评值当统计量对外讲（这会成为专业评委的第一个问题）。
- 可行性：留痕/页面展示为主；**1–2 天**。
- 验收：任一笔判定都能展开看到依据；材料里"confidence"的表述与实际口径一致。
