## 二、本轮新增与修复（已改，已验证）

### 1. `keeper.js` 误判「结算需要 operator 钥匙」（P1，真 bug）

- 位置：`04-脚本/keeper.js:219`（修改前）
- 现象：`if (SETTLE && VARIANT !== "V3")` 要求签名账户必须是合约 operator。
- 事实：`settleExpired` 只有 **v2** 带 `onlyOperator`；v3 / v4 / v5 都没有（它只减敞口、不付款）。写「不是 v3 就要」会把 v4/v5 一起拦死 —— 一把普通 keeper 钥匙明明能合法结算，却被脚本自己拒掉。
- 修法：改成正向条件 `const NEEDS_OPERATOR_SETTLE = VARIANT === "V2";`，注释写清「哪些版本真的要」而不是「哪些不要」。

### 2. `keeper.js` 版本参数静默降级（P1，真 bug）

- 现象：`VARIANT` 只认 `--v5` / `--v3`，敲 `--v4` 会**静默**落到 v2。
- 后果：v2 的 `policies()` 是 15 字段、v4/v5 是 16 字段 —— ethers 按 ABI 解出来的对象整体错位，**页面不报错，只报假数**。这正是本仓库历史上踩过的坑（v5 迁移时声明与调用点不同步）。
- 修法：四版本白名单 `["V2","V3","V4","V5"]`；出现 `--vN` 且不在白名单内直接抛错。

### 3. `keeper.js` 默认轮询 15 s → 1800 s（口径统一时已改）

与 `RainProof-Feed` 计划任务的 `PT30M` 同口径，注释写明「30 分钟」。

### 4. `04-脚本/setgrid-v5.js`（新建，补 P1-8）

- 存在理由：湖北 118 区划是 `open-hubei.js` 一次性脚本开的，**之后没有任何东西复核过「链上 244 格（122 区划 × 12h/24h）是否等于定价表」**。定价表改了、链上没改，没人会发现。
- 用法：
  ```bash
  node setgrid-v5.js              # 干跑：只比对，不写链
  node setgrid-v5.js --check      # 只读核验，有漂移退出码 2（可接门禁/监控）
  node setgrid-v5.js --send       # 真写（多签两票）
  ```
- 实测：**244 格零漂移**（12h 1.80–6.70 元、24h 2.40–10.50 元）。

### 5. `04-脚本/datasource-health.js`（新建，补 P1-6）

- 读 `09-AI判定留痕/v5-feed-trace-*.json` + `raw/`，输出三类指标：
  1. **Open-Meteo（外部）**：请求格数、本机留档报文数、服务端生成耗时 p50/p95/max
  2. **三模型共识（内部闸门）**：受理/拒收率、模型离散度分位（对照 `TOL_ABS = 2.5`）、拒收最多的区划
  3. **上链**：进批格数与占比
- 首跑（16 轮、672 格）：受理率 99.85%、拒收 1 格（420626 保康县）、离散度 p95 = 2.8 mm（贴着但未越 `TOL_ABS=2.5` 的单模型判定线）、进批率 15.77%。
- 健康判据用**拒收率 > 10%**（退出码 2），**不用「可用率」** —— 最初版本报了一个「可用率」，发现 `raw/` 有 50 MB 上限会清旧报文，这个数会恒等于 0，属于会误导人的假指标，已删掉。
- 用法：`npm run health` / `npm run health:save`（写 JSON）/ `node datasource-health.js --json`。

> 顺手记一条工程教训：`generationtime_ms` 是 Open-Meteo **服务端**生成耗时（p50 0.1 ms），不是网络往返延迟。标成「接口延迟」就是错的，已在输出里注明「不含网络往返」。

### P0-A `claim()` 没有宽限期 —— 错过窗口即永久失去赔付

- 位置：`03-合约/RainDeliveryInsuranceV5.sol:464` `require(block.timestamp <= p.endTime, "policy expired")`
- 后果：保单到期后，即使降雨成立、判定已上链、池子有钱，`claim()` 也一定 revert。到期后唯一的出路是 `settleExpired`（释放敞口、**不付款**）。
- 这不是理论风险：本轮真发生过 —— 计划任务的电池策略把 `RainProof-Feed` 停了 12.6 小时，最老喂价一度只剩 6.7 小时保鲜余量。若同类停摆在保单窗口内发生，骑手会**白白失去一笔本应赔付的钱**。
- 建议（v6）：`claimGrace`（如 7 天）后仍可领；或把条件改成「判定提交时间在窗口内即可领」，与领取时间解耦。短期运营兜底：`--interval=60` 的 keeper 常驻 + preflight 检查喂价新鲜度。

### P0-B `settleExpired` 批量里一张未到期，整批 revert

- 位置：`V5.sol:500` `require(block.timestamp > p.endTime, ...)` 在循环体内
- 后果：keeper 传一批 ID 时只要混进一张没过期的，整笔失败。脚本已用「批量失败 → 逐张重试」兜住（`keeper.js:115-128`），但那是**脚本兜合约**：多付一轮 gas + 一轮 RPC。
- 建议（v6）：`if (block.timestamp <= p.endTime) continue;`

### P1-C `setRegionActive(code, true)` 能绕过 `registerRegion`

- 位置：`V5.sol:368-373`
- 现象：`require(regions[code].active || active_)` 允许 `active_ = true` 直接通过；但只有 `registerRegion` 会 `regionCount += 1`，且只有它校验名字非空。
- 后果：用一个从未注册的码调用 `setRegionActive(x, true)`，会得到一个 `active=true`、`name=""`、且**不进 regionCount** 的区域。术语上「已开通区划数」从此对不上。
- 影响面：只破坏运营统计与不变量，不影响资金。当前链上 `regionCount = 123` 与实际 active 集合一致（已复核），属**潜在**缺陷。
- 建议（v6）：`require(regions[code].active || bytes(regions[code].name).length != 0, "unknown region")`，或在里面补 `regionCount` 记账。

### P1-D `_feed` 的累计雨量无上界

- 位置：`V5.sol:332-356`
- 现象：`cumulativeMm` 只校验「不得回退」，没有上界。operator 一笔就能写到 2^256，所有在保保单立刻满额可赔。
- 这是运营方信任假设（多签 2/3 缓解），但合约层零护栏。建议 v6 加上界（如单次增量 ≤ 500mm）或写入速率限制。
- **答辩口径**：被问「谁保证数据不造假」时，标准答案是「三方模型交叉验真 + 多方共管 2/3 授权 + 全程留痕可复算」，不要声称「合约阻止了造假」—— 合约只阻止了**数据回退**。

### P1-E `refundPolicy` 允许 operator 单方替骑手退保

- 位置：`V5.sol:516` `require(msg.sender == p.payer || msg.sender == operator, ...)`
- 后果：暴雨已成事实、赔付即将触发时，operator 可以强制退保（只退保费给付款方），把赔付责任消掉。
- 属信任假设，但**没写进风险表**。建议补进 `01-项目计划书` P12 / `路演-评委问答` 的「运营方权力边界」条目，并考虑 v6 去掉 operator 这条旁路。

### 已核查为「不是问题」的三处

- `claim` 与 `settleExpired` 的敞口扣减：由 `block.timestamp <= endTime` / `> endTime` 天然互斥，**不会重复扣减**。
- `refundPolicy` 与 `claim`：由 `effectiveFrom > now` / `now >= effectiveFrom` 天然互斥。
- `policyStatus()` 与 `payoutOf()` 读数口径不一致（前者用当前雨量、后者用判定快照）——**已知（A16）**，keeper 已用 `payoutOf() > 0` 兜住，不重复记。

### 一条「现在不触发」的潜在泄漏

- `_buy` 把 `rainfallAtBuy` 记在**买入时刻**，而 `claim` 算 `during = rainfallAtJudgement - rainfallAtBuy`。若 `coolingPeriod > 0`，冷静期内下的雨会算进赔付。
- 当前链上 `coolingPeriod = 0`（`effectiveFrom == startTime`），**该路径不成立**。但合约允许设到 30 天，一旦重新开启冷静期就会打开这个口子。
- 建议：v6 把基线改成 `effectiveFrom` 时刻的读数（懒记录），或在条款里明确「冷静期雨量不计」。
