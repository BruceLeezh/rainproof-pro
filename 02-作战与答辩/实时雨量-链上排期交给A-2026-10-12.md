## 2. 已定：**不自动化**，现场手工喂一次（A 的结论，用户 2026-10-12 拍板「仅执行这一条」）

### 2.1 为什么钱不是问题

| 事实 | 证据 |
|---|---|
| 677 / 968 同价 **20.0 Gwei** | `02-作战与答辩/审计报告-A侧处置-2026-10-07.md:47`（A 实测） |
| `updateRainfall` 实测 **47,719–47,731 gas** ⇒ ≈**0.000954 BOT/次** | 同文件 `:51` |
| 每小时喂 ≈ 0.023 BOT/天；最保守每 12 小时喂 ≈ **0.002 BOT/天** | 同上换算 |
| 工具早就有了 | `04-脚本/push-rainfall.js`（`npm run push` / `npm run refresh` / `npm run status`），另有 `04-脚本/keeper.js` |

### 2.2 代价在密钥，不在 gas

- `updateRainfall` 是 `onlyOperator`（`03-合约/RainDeliveryInsuranceV3.sol:340`）。想让链上时间戳自己变新，就得让**某个程序自动签名**：要么把 677 的 operator 从 **2/3 多签** `0x676b791da72Ef072718c9f078377bF21be1b160f` 换成一把单签热钥（`transferOperator` `:569`），要么把多签私钥塞进服务器（更糟）。
- 而那把 operator **同时握着 `withdrawPool`**（`:612`）⇒ 热钥泄漏 = 池子可被提走。
- 也就是说：自动化买到的只是「链上时间戳自动变新」的观感，付出的却是**把多签降成单点**。
- 另外，仓库里现在也没有任何定时器（`.github/workflows/` 只有 `gates.yml` + `deploy-demo.yml`，全仓 `schedule`/`cron` 零命中）。

### 2.3 结论与动作

**不自动化。** 链上读数是真的、可查、带块高与时刻；要新鲜，人工喂一次就够：

```bash
cd 04-脚本
npm run status    # 先看是否在 24h 窗口内（每行末尾「基线 剩 Xh」必须 > 0）
npm run refresh   # 同值重发，只刷时间戳（1 笔 ≈ 0.000954 BOT）
```

这一步已经写进现场清单：`02-作战与答辩/展示当天操作卡-2026-10-08.md` §一「上午必做：刷新喂价」。

### 2.4 「自动变新」的正路记进赛后 v3.1

正路是**独立 feeder EOA 只拿喂价权**（喂价权与提款权拆成两个角色）。那要改合约、解冻另立 v3.1 —— 是一次**合约改动**而不是运维配置，且与「不动已部署源码、保住『链上字节码 = 源码』证据链」冲突 ⇒ **赛期不做**，只在赛后 v3.1 的 backlog 里记一条。
