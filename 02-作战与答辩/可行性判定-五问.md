## 1️⃣ 参考农业保险标准：能给的锚点是**赔付率**，不是杠杆

### 判定：方向要改

**农业保险里没有"杠杆标准"这个东西，只有赔付率标准。**

现实中的天气指数保险（政策性农业保险的一支）受两层约束：

| 层 | 内容 |
|---|---|
| **赔多少** | 以"产量损失"或"气象指数"为触发，且**普遍是分档赔付**，不是单一阈值二元赔付 |
| **赔多少比例** | 监管与补贴框架围绕**综合赔付率**转（通常引用的口径在 70%~75% 量级，超额部分进入大灾风险准备金） |

### 为什么锚错对象会反向

```
杠杆 L = 赔付率 ÷ p          （推导：赔付率 = p × L）
```

农险锚的是**赔付率**。把**赔付率上限**从演示用的 60% 提到农险口径的 70~75%（⚠️ 本文的 60% / 75% 都当**上限**用，**不是"目标赔付率"**；这里是 2026-10-07 的敏感性口径，现行 v3 正解见 `10-金融与定价/定价逻辑与正收益保障-B-2026-10-07.md:179`）：

| 赔付率上限 | 武汉建议保费（p=0.754%，安全附加 θ=0.5） | 隐含杠杆 |
|---|---:|---:|
| 60%（现用） | 0.00019 | 53× |
| **75%（农险口径）** | **0.00015** | **66×** |

**方向：赔付率越高 → 保费越低 → 杠杆越高。** 所以"参考农险定杠杆"这个问法本身会把人带偏 —— **该定的是赔付率，杠杆是它的函数**。

### 待核

> ✅ **已核（2026-10-07，选手 B 补注，正文未改）**：本问引用的「70%~75% 量级」经核**表述不准** —— 财政部《农业保险大灾风险准备金管理办法》（2014-01-01 施行）中，**70% 是"低于才认定承保盈利、需计提利润准备金"的线（第十条），75% 是"超过才可动用大灾准备金"的线（第十四条）**，二者是两条不同门槛，不是一个区间。原文与链接见 `02-作战与答辩/P1-18-待核四项-核实记录.md` §一。
> **结论不受影响**：监管框架确实围绕综合赔付率转，「锚错对象」这个判断仍然成立。只是对外表述要改成 70/75 两条线，见核实记录里的正确讲法。

⚠️ 农险综合赔付率的具体口径（70%？75%？是否分险种）**未能联网核实**，写进任何材料前必须核对原文。

## 2️⃣ 动态杠杆能否消除"按预报套利"

### 判定：**单独做不可行**

### 机制：问题不在杠杆，在**定价所用的信息集**

```
公平保费 = E[损失 | 购买时刻的公开信息 I_t] × (1+θ) ÷ 赔付率
```

我们目前用的是**无条件**历史概率 `p`（"随便哪一天"的触发概率）。但投保人是在**有条件**地决策 —— 他看到预报才买：

```
投保人买  ⟺  E[损失 | I_t] > 保费
```

**这不是杠杆问题，是逆选择。** 调高或调低杠杆，只改变套利门槛，不消除套利。

### 更尖锐的一点：预报越准，这个产品越难以保险形式存在

> 如果预报完全准确，那么"是否赔付"在购买时就已确定 —— 保费必须等于赔付额（零不确定性、零风险），**保险本身就不存在了**。
>
> 也就是说：**预报准确度与这个产品的可保性是反向关系。**

### 可行路径（按代价从低到高）

| 做法 | 机制 | 效果 | 代价 |
|---|---|---|---|
| **定价随预报浮动** | 保费 = 预报条件下的 E[损失] | 直接消除套利 | 高（接预报 API + 定价逻辑重做） |
| **购买时滞 t+N** | 只能买 T 天之后的保障期 | 使 `E[损失\|I_t] ≈ p`，静态定价近似成立 | 中（见 §5） |
| **限购 + 保额上限** | 每人每期一份、保额有顶 | 限制套利规模，治标 | 低 |

**结论**：若坚持静态定价，必须靠"时滞 + 限购"压住套利，否则池子会被系统性抽干。

## 3️⃣ 骑手身份认定

### 判定：**纯链上不可行。而且这条不解决，产品在法理上不是保险。**

### 两个绕不过去的保险原则

| 原则 | 要求 | 现状 |
|---|---|---|
| **保险利益原则** | 被保险人对保险标的（收入）须有保险利益 | ❌ 任何人能付保费就能买 → 是对天气下注 |
| **损失补偿原则** | 赔付不超过实际损失（定额给付型则须有身份资格） | ❌ `PAYOUT` 固定，不校验是否有真实损失 |

### 身份信息在哪里

**只有平台有。** 在职状态、接单记录、活跃度全在平台侧，链上没有任何信息源。

| 路径 | 可行性 | 说明 |
|---|---|---|
| 平台作为投保人/代理人（B2B2C）+ 平台签名凭证 | ✅ **可行** | 身份由平台 attestation 确认，链上只做结算与留痕 |
| KYC + 平台在职证明（每次续保核验一次） | ⚠️ 半可行 | 依赖平台配合，核验成本高 |
| 纯链上 DID / 链上身份自证 | ❌ **不可行** | 链上没有"你是不是骑手"的信息，凭空发身份＝伪造保险利益 |

**这条同时回答了一个隐含问题**：为什么我们的商业模式**必须**找平台？不只是获客成本 —— **没有平台就没有保险利益，产品就不成立**。

## 4️⃣ 雨量标准与分档赔付

### 判定：**完全可行。这是五问里唯一能立刻提升产品档次的。**

中国有**两套**可直接引用的权威标准，第二套天生就是分档的：

### (a) `GB/T 28592-2012《降水量等级》` —— 按时间窗分级

| 24 小时降水量 | 等级 |
|---|---|
| 50.0–99.9 mm | 暴雨 |
| 100.0–249.9 mm | 大暴雨 |
| ≥ 250.0 mm | 特大暴雨 |

### (b) 气象灾害预警信号（暴雨蓝/黄/橙/红）—— **同时含"雨强"与"时间窗"**

| 预警 | 触发条件 | 建议赔付比例 |
|---|---|---:|
| 🔵 蓝色 | 12 小时内降雨量将达 50mm 以上 | 25% |
| 🟡 黄色 | 6 小时内降雨量将达 50mm 以上 | 50% |
| 🟠 橙色 | 3 小时内降雨量将达 50mm 以上 | 75% |
| 🔴 红色 | 3 小时内降雨量将达 100mm 以上 | 100% |

### 为什么这套能直接修掉我们现有的漏洞

现有设计的毛病是：**「50mm」被套在任意 1~72 小时窗口上**，导致长保单更容易获赔（72h 的触发概率是 24h 的 5.2~8.1 倍）。

而**每一档预警信号自带时间窗** —— 阈值与时间窗是绑定的。分档表一列出来，"为什么是 50mm""为什么是 72 小时"两个问题同时消失，并且"我们按国家预警信号分档赔付"这句话本身就自带权威性。

### 可行性

高。合约把单阈值 `THRESHOLD` 改成**四档阈值数组 + 赔付比例数组**，`claim()` 按命中的最高档位计算赔付即可。

### 待核

⚠️ 两套标准的具体数字（尤其预警信号的时限与量级口径）**必须核对原文后**才能写进材料。

## 5️⃣ t+3 购买（最早只能买 3 天后的保障）

### 判定：**技术可行、方向正确，但是缓解不是根治**

### 技术上

```solidity
require(startTime >= block.timestamp + 3 days, "policy must start 3+ days out");
```

### 为什么有效

3 天后的降水预报不确定性已经显著变大，`E[损失 | I_t]` 会向无条件概率 `p` 收敛，静态定价的误差随之缩小。

### 为什么不根治

- **季节尺度信息仍然公开**：雨季/旱季、台风季是常识，套利者仍能在有利季节集中购买；
- t+3 只削掉短期预报的信息优势，**削不掉气候尺度的信息优势**。

### 三个必须一起想的代价

| 代价 | 说明 | 处理方向 |
|---|---|---|
| **保险实用性下降** | 买不到"今天/明天"的保障 | 但这**更符合保险定义** —— 保险本来就该是事前投保 |
| **资金占用** | 保费预收、3 天后才生效 | 需处理未起保退保；准备金与流动性须按"未生效保单"计提 |
| **合约复杂度上升** | 需引入起保时间字段，`rainfallAtBuy` 快照时点随之改变 | 状态机要重画 |

### 最有说服力的现实对照

> **农业天气指数保险的通行做法，是"在播种前提前卖整季"——购买时无法预知后期天气。**
>
> 也就是说：**t+3 不是在给我们的产品打补丁，而是把它拉回天气指数保险的本来做法。**
> 反倒是我们原来"即时购买、次日生效"的设计才是异类 —— 它天然给短期预报留了套利空间。

## 6. 汇总：若要做成"真产品"，最小改造清单

| 改造 | 对应问题 | 代价 | 是否阻塞"叫保险" |
|---|---|---|---|
| 赔付率**上限**锚定农险口径（约 70~75%） | ① | 极低（改常数） | 否 |
| 赔付改为**四档预警分档** | ④ | 中（合约改结构 + 重新部署） | 否 |
| 购买滞后 **t+3** + 每人限购一份 | ②⑤ | 中（加字段 + 状态机） | 否 |
| 保费**随预报浮动**（或明确不做，靠 t+3 兜底） | ② | 高（接预报 API + 定价重做） | 否 |
| 身份 = **平台 attestation** | ③ | 高（必须商务对接平台） | **是** ✅ |

**只有最后一条是"不做就不成立"** —— 其余都是"做得更好"。
