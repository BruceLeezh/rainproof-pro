## 四、关键证据：这笔交易的 gas 是**双峰**的

10 次运行里 `[3] 喂价` 段那笔 `updateRainfall(1, 80)`：

| 运行 | 请求的 `gas` | 回执 `gasUsed` | status |
|---|---|---|---|
| s1 · s2 · s4 · s5 · s7 · s8 | `49659` | `49659` | `0x1` ✅ |
| **s9** | **`49659`** | **`49659`** | **`0x0`** ❌ |
| s3 · s6 · s10 | `52459` | `52459` | `0x1` ✅ |

**`52459 - 49659 = 2800`** —— 这个差值正好是一个「冷 account / 冷 slot 访问」的量级。
而且每一次发出去的 `gas` 字段**恰好等于该次 `eth_estimateGas` 的返回值**（ethers v6 的行为：不额外加 buffer）。

**读法**：ganache 对同一笔交易估出的 gas 会在两个档位之间跳；ethers 拿这个裸值当 `gasLimit`；
一旦某次「估计落在低档、实际执行落在高档」，这笔就**耗尽 gas 回滚**，
`gasUsed == gasLimit`、`status = 0x0`、`revert = null` —— 与观察到的现象完全一致。

**旁证（很硬）**：只要在该交易**之前**多插一次异步 RPC（`_audit_stat/mkprobe2.py` 在 `feed` 里先 `await c.rainfall(regionId)` 打一行日志），
**6 次运行全部通过**。纯粹改时序就消失 → **竞态/估 gas，不是逻辑**。

## 五、建议的修法（一行，你的地盘你定）

```js
const feed = (regionId, mm, confidence = 90, sources = 3, tag = "") =>
  c.connect(operator).updateRainfall(
    regionId, mm, H(`snapshot:${regionId}:${mm}:${tag}`), confidence, sources,
    { gasLimit: 300000n }   // ← 别让 ethers 直接用估出来的裸值当上限
  );
```

同类风险点（同类"估出来直接用"的交易）：`e2e_contract.js:99` 的 `fundPool`、`:130/:132/:135/:152` 的喂价负例、
以及所有 `buyPolicy` / `claim`。要更省事可以只写一次：给 `operator` / `a` / `b` 这几个 signer 的连接统一加 overrides。

> ⚠️ 顺带提醒：**别只缩小到"给这一笔加 gas"** —— 双峰说明 ganache 的估计在这条链上是**系统性地不可靠**，
> 别的笔也可能撞。要么统一加 buffer，要么在末尾加一道"重试一次"的兜底。
> 我的看法是加 buffer 更干净：测试脚本不该有重试语义。
