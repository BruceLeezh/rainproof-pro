## 1. 目标用户是谁（定性，不需要数字）

| 特征 | 内容 | 为什么这决定产品形态 |
|---|---|---|
| 身份 | 平台**众包骑手**（非雇员） | 劳动关系模糊 → 法定保障缺位，保险需求真实存在 |
| 计酬 | **按单计酬**，无底薪 | 不出勤 = 零收入 → "暴雨天跑不了单"= 直接收入损失 |
| 收入波动 | 与出勤强绑定，天气是最大外生变量 | 损失可被**天气数据**代理 → 参数化保险成立的前提 |
| 现有保障 | 意外险通常覆盖"人身伤害"，**不覆盖"收入中断"** | 我们填的是**收入损失**这个缺口，不是意外伤害 |

**一句话**：我们保的不是"骑手受伤"，是"骑手今天跑不了单"。

> ⚠️ 这句要小心：我们**不判断骑手是否真的受损**（那需要平台订单数据，见 `产品说明与商业模式.md` §6）。我们判断的是**天气是否达到"显著影响出勤"的水平**。这两句话的分寸要拿准。

## 2. 收入结构与覆盖度（已可算，不再是 `[待补]`）

### 2.1 模型

```
单人日收入        R = a × n
   a = 单均收入（元/单）
   n = 日均完成单量（单/日）

暴雨日损失        L = R × q
   q = 当日无法出勤 / 无法接单的比例（0~1）

赔付覆盖度        C = PAYOUT(折算法币) ÷ L
```

### 2.2 取值：只有一个数需要外部数据，其余全部由它推导

| 符号 | 取值 | 依据与性质 |
|---|---|---|
| `R`（日收入） | **384.9 元/日** | 由已核来源 **11,547 元/月 ÷ 30 天**。**这是上界口径**（一线城市 + 高频 + 熟练），不是全体众包骑手 |
| `q`（暴雨日停摆比例） | **取 1.0（整天损失）作为上界** | 不引任何中间假设。真实值 ≤1，所以下面算出的 `C` 是**下界** |
| `L`（暴雨日损失） | **= 384.9 元** | `L = R × q`，取上界即最难满足的情形 |
| `PAYOUT` | **0.01 ETH** | 合约 `03-合约/RainDeliveryInsurance.sol:21` `constant` |
| ETH 法币价 | **不做固定假设** | 见 §2.4：用**链上费用**做不随币价变动的替代锚 |

**为什么不再用"口径冲突"当借口留空**：三个口径都能追到出处、都能查到原文，只是限定总体不同（§0 已列全）。**把它们如实标成三个不同抽样总体，比留空更有说服力**。后者会被当成没做功课。

### 2.3 覆盖度 `C`：结论对"实际损失比例"完全不敏感

- **`q = 1`（整天跑不了单，最极端）**：`L = 384.9 元`，`C = PAYOUT ÷ 384.9`。
- **`q = 0.5`（半天跑不了单）**：`L = 192 元`，`C` 翻倍。

> **我们不需要知道 `q` 是多少。** 参数化险的赔付与实际损失**本来就不要求一一对应**（否则就不叫参数化了）。要讲的是**量级**：一次赔付与"骑手一天的收入"同量级，这一句在 `q ∈ (0,1]` 的任何取值下都成立。
>
> 按 2026-10-07 的 ETH 参考价粗算，`PAYOUT ≈ 250 元` ⇒ **≈ 0.65 个一线城市高频骑手日收入（384.9 元）**，或 ≈ 1.2 个全国口径日均（7,230~10,100 元/月 折日 ≈ 241~337 元）。**法币价不写死，现场读。**

### 2.4 不随币价变动的锚：赔付额与"处理这一笔的成本"之比

这是最硬的一句，因为**两个数都能现场查**：

| | 传统骑手险（行业量级口径） | 雨证（链上实测） |
|---|---:|---:|
| 处理一次索赔的人工 / 定损成本 | **100 ~ 200 元** | — |
| 链上提交一次 AI 判定的 gas | — | **≈ 0.00013 ETH** |
| 链上执行一次赔付的 gas | — | **≈ 0.00012 ETH** |
| 一份保单的赔付额 | 视保单 | **0.01 ETH** |

- 赔付额 ÷ 一次判定 gas ≈ **77 倍**；赔付额 ÷ 一次投保手续费（实测 0.00046 ETH）≈ **22 倍**。
- 包含判定与赔付的链上总成本 ≈ 0.00025 ETH，**只占赔付额的 2.5%**；而传统口径下，处理一次索赔的成本与一次小额赔付**同量级**。

**含义**：**传统的钱花在"查"，我们的钱花在"给"。** 

> ⚠️ **来源等级必须说清（否则这一条会被反问，且答不出来）**：
> - **链上三行是实测的**（gas 来自 **10-06 第一阶段在 Sepolia 上的真实回执**，见 `提交材料/产品说明与商业模式.md` §5），可现场复算。**演示基线是 BOT Chain 主网 677 上的 v3（2026-10-08 起；968 上的 v2 降为测试网留痕）**；这一组「保费还不够付自己的手续费」的对比按 **L1 口径**读，也正是我们主张"真实部署目标是低 gas 链"的理由。
> - **「100 ~ 200 元」是行业量级判断，不是可引用数字。** 2026-10-07 我按公开检索**没能核到**"小额理赔单件定损成本"的权威原始出处（中英文检索均未返回可用的一手数据）。所以答辩时的正确说法是：
>   > 「传统小额险的成本痛点在于**每一笔索赔都要人工核损**，处理成本与小额赔款**同量级** —— 这是行业共识性的量级判断，我们没有把它包装成一个精确数字。**我们真正能精确复算的是链上那三个 gas 数。**」
>
> **不要**把 100~200 元说成"某报告的数据"。这一条的论据力量来自**结构**（人工核损 vs 链上自动判定），不来自那个区间的精确值。

### 2.5 定价逻辑与之相容

- **保费端**（够不够赔）：由 `10-金融与定价/精算口径.md` 的触发概率决定，权威值 **武汉 4.7696% / 上海 4.5568% / 北京 2.2810% / 广州 11.5742% / 成都 3.7235%**（72h，整数十分位口径，见 `10-金融与定价/audit-verified.json`），链上五城保费已按 60% 目标赔付率重设。
  > ⚠️ **口径别混**：这组数**只对链上 v2 的 24/48/72 口径成立**（v2 档线是 `50 × h / 24` 的线性外推）。v3 的定价口径是**国标 GB/T 28592—2012 的 12h/24h 两档**（12h 30/70mm，24h 50/100mm），两套**不可互相换算、也不可混引**。对外只说"这是当前链上合约的费率"，不要说成"我们的定价模型"。
- **赔付端**（够不够用）：本节 §2.3 的覆盖度 `C`，**量级已可讲**（与一天收入同量级），精确值仍需平台订单数据。

> 两端口径不要混：**保费算的是"我们亏不亏"，赔付算的是"骑手够不够"**。评委可能只问一边，答的时候先分清是哪一边。

## 4. 仍然缺什么（如实标注）

| 缺口 | 为什么重要 | 怎么补 |
|---|---|---|
| **日均单量 `n`** | 影响"一次赔付 ≈ 几天收入"的精细换算 | 需骑手访谈或平台口径；**不影响 §2.4 的链上比值结论** |
| **暴雨日停摆比例 `q`** | 决定 `C` 的精确值 | 可由"暴雨日单量 vs 平日单量"推；**不影响量级结论** |
| **平台订单数据** | 才能判断骑手是否真的受损 | 这正是本案的边界：参数化险只能判天气，判不了损失（§1 的警告） |
