## 0. 为什么是 12h / 24h —— 本轮唯一的改动理由

**GB/T 28592—2012《降水量等级》§3 原文：「降雨量按 12 h，24 h 两个时间段进行划分」。国标只有这两个时段。**

表 1「不同时段的降雨量等级划分表」（单位 mm）：

| 等级 | 12h 降雨量 | 24h 降雨量 |
|---|---|---|
| 微量降雨（零星小雨） | <0.1 | <0.1 |
| 小雨 | 0.1~4.9 | 0.1~9.9 |
| 中雨 | 5.0~14.9 | 10.0~24.9 |
| 大雨 | 15.0~29.9 | 25.0~49.9 |
| **暴雨** | **30.0~69.9** | **50.0~99.9** |
| **大暴雨** | **70.0~139.9** | **100.0~249.9** |
| **特大暴雨** | **≥140.0** | **≥250.0** |

所以 v3 的保障时长就是 **`[12, 24]`**，档线直接取国标原件的暴雨 / 大暴雨下限 —— `THRESHOLDS = { 12: [30, 70], 24: [50, 100] }`。删掉 48h/72h 的三条理由：

1. **国标没有 48h/72h 档。** v2 的 `thresholdOf(h) = 50 × h / 24` 是**线性外推**，把 72h 暴雨线推到 150mm、特大暴雨线推到 750mm。说"国标 72h 暴雨线"是不成立的。
2. **线性外推被国标自己的两列证伪。** 国标 24h/12h 的比值是 **1.667 / 1.429 / 1.786**（暴雨 / 大暴雨 / 特大暴雨），**没有一个是 2**。线性缩放等价于假设比值恒为 2。
3. **实测 72h 是"更贵、更难赔"的一档。** 11 年逐小时五城：12h 档 0 触发率 0.4273%~1.2954%，24h 0.4377%~1.4200%，48h 0.1899%~0.7750%，72h 0.1090%~0.5625% —— **72h 的触发率只有 12h 的 1/4 左右**。也就是说 72h 让买家**多付约 4 倍保费、换到更低的中奖概率**（武汉为例）。这不是保障，是反着的。
   ⚠️ 这个「1/4」是**跨档线**比的（v2 72h 的 150mm 对 v3 12h 的 30mm），**对外引用必须带档线**；**同基数**（武汉，拿链上 v2 自己的 24h 与 72h 比）是「保费 0.0002 → 0.0008 多付 4 倍、触发率 0.4377% → 0.2117% 中奖率降到 **1/2.07**」。

> 删掉 48h/72h 后格数从 60 降到 **40**（5 区域 × 2 时长 × 4 承保渠道），批量带从 180 降到 **120**。

## 1. 一句话

v2 已经是 **地区 × 时长的 15 格表**（`premiumGrid[region][hours]`，24h/48h/72h 逐格不同价）+ 一条 operator 承保加价路径 `aiPremium`；**v3 补上缺的三个维度（骑手类型 / 场景 / 购买量），变成 5 个维度、40 格零售价 + 120 格批量价**，并且第一次让价格直接反映两件在微保险里压倒一切的事：**买家的择时能力**，和**一次判定能覆盖多少份保单**。

## 2. 五个维度，以及为什么是这五个

| 维度 | 取值 | 为什么它必须进价格 |
|---|---|---|
| **地区** | 武汉 / 上海 / 北京 / 广州 / 成都 | 触发概率差 **3.0 倍**（12h 无条件：广州 1.2954% vs 北京 0.4273%）。同一场雨在不同城市的"值多少钱"完全不同 |
| **保障时长** | **12h / 24h**（国标唯二的两档） | 触发概率随窗口上升，但**不是线性**。12h→24h 的保费系数实测 **1.000~1.382 倍**（北京平台团体 12h 与 24h 同价 —— 北京 24h 大暴雨概率与 12h 几乎一样，这是正确结论不是 bug） |
| **用户类型** | 众包自助 / 认证骑手 / 平台团体 | 决定**择时能力 κ**。这是全表最大的价格杠杆：成都 24h 从 κ=0 的 0.00031 到 κ=1.0 的 0.00099，**3.2 倍** |
| **使用场景** | 自助投保 / 平台代付 | 平台代付走**批量价**（一次 AI 判定覆盖整批），自助投保每份各触发一次判定 → 固定成本差（N=1 → N=1000）**逐格 84×~326×**（武汉 12h 平台团体格 = 198×） |
| **购买量** | 1 / 10 / 50 / 100 / 500 / 1000 份 | 同上，把"判定 gas"这个固定成本按份摊薄。**微保险里固定成本常常大于风险保费本身** |

### 2.1 维度之间不是独立的乘数

地区、时长是**概率维度**；用户类型、使用场景、购买量是**机制维度**。做成两个独立乘数会把同一份逆向选择算两遍（例如"认证骑手"和"平台代付"高度相关，因为它们本就是同一个平台合约的两个条件）。

所以 v3 用一张**合法性表**：`(用户类型, 使用场景)` 6 种组合里只有 4 种合法，每种给一个 κ：

| seg | 用户类型 | 使用场景 | κ | 说明 |
|---|---|---|---|---|
| 0 | 平台团体 | 平台代付 | **0.00** | 平台整批为在册骑手投保，投保时点与天气无关 —— 择时归零，唯一"干净"的渠道 |
| 1 | 认证骑手 | 平台代付 | **0.15** | 认证 + 平台代付结算，个人择时只剩微弱残差 |
| 2 | 认证骑手 | 自助投保 | **0.55** | 身份绑定 + ≥1 天冷静期，削掉短期择时，削不掉"雨季才想起来买" |
| 3 | 众包自助 | 自助投保 | **1.00** | 无身份绑定、随时可买 —— 纯靠气候学"只买雨季"就能拿到的上限 |

非法组合：`(平台团体, 自助投保)`、`(众包自助, 平台代付)`。理由：团体单必须由平台发起；没有身份绑定的个人不能享受平台代付的批量价（否则"凑单"会成为新的逆向选择口子）。

### 2.2 κ 的含义与建模

κ 不是"打折系数"，是**投保时点的月度分布与风险月度分布的耦合强度**：

```
w_m = (1-κ)/nM + κ · rate_m / Σrate        （nM = 132 个月，rate_m = 该月触发率）
```

κ=0 → 各月等权（投保时点与天气无关）；κ=1 → 投保集中在高风险月份。

⚠️ **不能用 `rate_m^κ`**。干季 `rate_m = 0` 时 `0^κ = 0`，等于把全部干月权重清零，于是 κ 只有 0.15 也会给出 **18 倍**加载（幂律在零点处不连续）。线性混合式的上界是 `Σrate²/Σrate ≤ max_m rate_m`，加载倍数天然有界。

实测加载倍数（vs 无条件 p）：

| 区域 | 12h κ=0.15 / 0.55 / 1.00 | 24h κ=0.15 / 0.55 / 1.00 |
|---|---|---|
| 武汉 | 1.77× / 3.82× / 6.13× | 2.37× / 6.05× / 10.18× |
| 上海 | 1.59× / 3.20× / 4.97× | 1.66× / 3.56× / 6.61× |
| 北京 | 1.42× / 2.96× / 7.41× | 1.52× / 3.87× / 10.84× |
| 广州 | 1.43× / 2.04× / 4.13× | 1.44× / 2.58× / 5.14× |
| 成都 | 1.68× / 3.62× / 8.34× | 1.76× / 4.61× / **12.53×** |

（"加载倍数" = 该 κ 下某格的**点估计触发率** ÷ 该格的**无条件触发率**，从 `pricing-engine.json` 的 `pointRatePct` / `uncondPointRatePct` 逐格算得。）

> **⚠️ 这里的"触发率"是档位加权期望赔付比例 `E[f]`，不是"命中 ÷ 窗口"的二元 `p₁`。**
> 武汉 12h：`p₁` = 820 ÷ 96421 = **0.850437%**，`E[f]` = **0.444924%**，两者差约 **1.9 倍**（第 1 档只赔 50%）。
> `vsUncond`（加不加 κ 的比值）两种口径下几乎相同，因为这个差别在分子分母里约掉了；但**绝对值不能混引**。
> 口径三分见 `B端档位设计与不亏损证明.md` §1.2 与 `pricing_engine.js` 的字段注释。

### 2.3 考虑过、但没进价格的维度：骑手班次时段

"使用场景"最自然的延伸是**骑手一天里的班次**：10:00–20:00 跑单的人，凌晨三点的雨对他没有收入影响。既然合约赔的是"窗口内累计降水"，那按时段定价理论上能便宜很多。**我们算过，结论是它非但不便宜，而且更贵。**

算法：只累计班次内的雨量，档线**按班次小时数占窗口的比例等比缩放**（12h 窗口 ×5/12、×2/12；24h 窗口 ×10/24、×4/24）。这不是随便挑的缩放 —— 这正是"平均每小时强度不变"的含义。

1. **第一层（够不够）**：算了才知道它不便宜。反过来如果它便宜 5 倍，我们会被诱惑去卖一个"我上班时淋到才赔"的东西 —— 而那个东西恰好是**能靠自述班次来择时**的，和 §7 删掉的临灾档一个毛病。

## 3. 核心公式

每一格的价格由两个数取大，再量化到网格：

```
C(N, q) = JUDGE_GAS / N + PAYOUT_GAS · q            每份的链上执行成本
P_net   = ceil((E₉₇.₅ · PAYOUT_MAX + C(N,q)) / R*)  费率闸 —— 让"97.5% 分位情形"下的赔付率不超过 R*
F       = ceil(C(N,q) · (1 + M))                    成本地板 —— 覆盖执行成本 + 25% 加成
P(N)    = max(P_net, F)
```

| 常量 | 值 | 依据 |
|---|---|---|
| `PAYOUT_MAX` | 0.01 ETH | 合约 `PAYOUT_MAX`，两档中最高档（100% 档、大暴雨）全额赔付额 |
| `R*` | 60% | 目标赔付率。与 v2 的 `TARGET_LOSS_RATIO` 一致 |
| `E₉₇.₅` | 逐格分位数 | 月聚类块自举 4000 次（块长 = 1 个日历月，保留月内自相关），取 97.5% |
| `M` | 25% | 成本加成 |
| `JUDGE_GAS` / `PAYOUT_GAS` | 0.00013 / 0.00012 ETH | 2026-10-06 真链实测 |
| 网格 | **0.00001 ETH** | v2 的 0.0001 太粗：平台批量价落在 0.00002~0.0001，0.0001 网格会吞掉一半折扣 |
| `MIN_PREMIUM_ABS` | 0.00002 ETH | 合约硬地板（v2 是 0.0002，**必须降到 0.00002**，否则批量价全被拒） |
| `PREMIUM_CAP` | 0.002 ETH | **尊严上限** = 赔付上限的 20%。见 §5 |

**`P(N) = max(P_net, F)` 是全文最重要的一行。** 微保险里固定成本常常大于风险保费：零售口径每份固定成本 **0.00013053 ETH**，而平台团体渠道 10 格的 97.5% 风险保费只有 **0.00003278~0.00010142 ETH** —— **固定成本是干净渠道风险保费的 1.29~3.98 倍**。只按风险定价会卖一份亏一份；只按成本定价会在大灾城市赔穿。

> ⚠️ 口径注（复核时用得上）：分子 `0.00013053` 取的是**武汉 12h 平台团体那一格**的 N=1 固定成本；20 个平台代付渠道格的固定成本实际落在 `0.00013027 ~ 0.00013144 ETH`（极差 0.9%），**换哪一格结论都一样**。分母的 10 格区间是全表平台团体渠道的风险保费。两个数不同源（单格 ÷ 十格区间），这是刻意的保守写法。

> 关于网格：`CEIL_TICK` 从 `1e4` 改成 `1e5` **偏离了本仓 `audit_numbers.js` / `tier_design_b2b.js` 的既有约定**（那两处是 0.0001，服务于 v1 单点定价）。理由是批量价量级低于网格分辨率。零售价四舍五入到 0.0001 与 v3 值一致，差异只体现在批量档。

### 4.1 五个维度各自贡献了多少价差

| 维度 | 同一维度的极差 | 例子 |
|---|---|---|
| 地区 | **1.453×（12h）/ 1.544×（24h）** | 固定众包自助渠道（κ=1.00）：12h 北京 0.00053 → 广州 0.00077；24h 北京 0.00068 → 武汉 0.00105 |
| 时长 | **1.000~1.382×** | 北京 平台团体 1.000×（12h 与 24h 同价）→ 武汉/成都 众包自助 1.320~1.382× |
| 用户类型 + 使用场景 | **1.893~3.194×** | 最平 北京 12h（0.00028→0.00053）→ 最陡 成都 24h（0.00031→0.00099） |
| 购买量 | **−61.1%**（N=1→1000，中位比 0.389） | 武汉 24h 平台团体 0.00033 → 0.00013 档 |

**五个维度合起来的全表极差是 3.750×**（最低 北京 12h 平台团体 0.00028 → 最高 武汉 24h 众包自助 0.00105）。

⚠️ 3.750× 是**跨渠道**的合表极差，**不是"地区"极差**：地区行的 1.453×/1.544× 固定了渠道=众包自助。若把渠道/身份一起挪动去算"地区差"，等于把身份折扣记到地区风险名下，会把它放大 **2.4 倍**（3.750 ÷ 1.544）。

（"极差"= **固定其余维度**时的 max/min，从 `pricing-engine.json` 逐格算得，可用 §10 的命令复算。每个维度各自固定了哪些维度见上表第三列；地区行的两个数已纳入 `ref/check_doc_prices.js` 的整表标量门禁。）

**时长的系数为什么这么小**：先分版本说清楚 —— **"50mm 恒阈值套在任意窗口上"是 v1**（`RainDeliveryInsurance.sol`），那个口径下窗口拉长触发率涨 5~8 倍；**v2 已经把档线随窗口线性缩放**（`thresholdOf = 50 × h/24`），代价是第 2 档 `250 × h/24`（72h 即 750mm）在 11 年历史里一次都没触发（§6）。v3 回到**国标原件**（两档、非等比例），时长系数落在 **1.000~1.382 倍**。北京平台团体 12h 与 24h 同价，这是正确结论：北京 24h 触发概率与 12h 几乎一样。

## 5. 尊严上限与"卖不卖得动" —— 本批 0 格不卖

`sellable = P(1) ≤ PREMIUM_CAP`。**尊严上限 0.002 ETH**（按 1 ETH ≈ 25,000 元折算约 50 元），是赔付上限的 20%。

**本批 40 格全部可售，0 格触发上限。** 最贵的一格是武汉 24h 众包自助 **0.00105 ETH**（约 26 元），离上限还有 **1.90 倍**余量。

这不是"因为改了时长所以问题消失了"，而是**原来那 3 格不卖的全部成因就是 72h**：无身份绑定 + 雨季城市 + 最长时长，诚实价 0.00205 / 0.00211 / 0.00287 > 0.002。删掉 72h 之后，"众包自助"这个最贵渠道的最差格降到 0.00105 —— 报得出价，卖得动，也不需要在产品上开一个"我们不卖"的口子。

代价要说清楚：**"没有身份就报不出价"这个极端故事没有了。** §2.1 的身份分档现在靠的是 **κ 的价差**（同一区域同一时长，众包自助 0.00105 vs 平台团体 0.00033，**3.18 倍**），而不是"干脆不卖"。**身份验证仍然是价格动作，只是从"开关"变成了"倍数"。**

## 6. 档线：回到国标原件（v3 修掉的 v2 硬伤）

v2：`thresholdOf(hours) = 50 × hours / 24`，三档 = `[50h/24, 100h/24, 250h/24]`。

**问题**：档 2 的 250×(h/24) 在 11 年实测里几乎不可达。72h 要 750mm、48h 要 500mm —— 五城 11 年逐小时窗口**一次都没命中**。**这是"合约里写了一个永远不会赔付的条款"**，对骑手是虚假承诺。

v3 直接取国标表 1，**只有两档**：

| 时长 | 档 0 起点 | 档 1 起点 | 档位金额 | 出处 |
|---|---|---|---|---|
| 12h | **30mm** | **70mm** | 50% / 75% | GB/T 28592-2012 表 1 的 12h 暴雨 / 大暴雨下限 |
| 24h | **50mm** | **100mm** | 50% / 75% | 同表 24h 暴雨 / 大暴雨下限 |

**为什么不卖国标的第三档（特大暴雨）**：24h 的 ≥250mm 在五城 11 年逐小时窗口里**零命中**；12h 的 ≥140mm 只有 0.002%~0.007% 命中（武汉 4 次 / 上海 0 / 北京 2 / 广州 2 / 成都 7）。**我们刚刚骂过 v2 的 750mm 是永不到期的条款，不能换个出处再犯一次。**

⚠️ **但理由不是"它不可能发生"，而是"没有定价依据 + 表述诚实性"**（这个区分必须守住，否则等于用另一个 750mm 换掉这一个）：
- 样本离档线只差 **1.7%**（成都 24h 最大累计 **245.9mm** vs 250mm）；
- Rule of Three：96,409 个重叠 24h 窗折成约 `96,409 / 24 ≈ 4,017` 个独立窗，真实概率的 95% 上界仍有 **`3 / 4017 ≈ 0.075%/窗`**；
- 即便按这个上界，这一档的期望赔付也只有 `0.075% × 0.01 = 7.5e-6 ETH`，而**单份判定 gas 是 1.3e-4 ETH** —— 风险项只占固定成本的 **5.8%**。卖它既收不到钱，又给了一个几乎不可能兑现的承诺。

若确实要保留第三档的演示冲击力，见 [`v3-合约规格.md`](v3-合约规格.md) §「三档变体」——但那是产品演示选择，不是精算建议。

## 7. 为什么删掉了"临灾加保"这一档

早期草稿里还有第 6 格：`(认证骑手/众包, 预警增保)`，定价用条件触发率 `P(触发 | 投保前 24h ≥ 25mm)`。**v3 删了它**，三条理由：

**① 合约的冷静期在生产口径下已经把它锁死了。** `RainDeliveryInsuranceV2.sol:228` 写的是 `p.effectiveFrom = block.timestamp + coolingPeriod;`（`:68` 合约**默认** `coolingPeriod = 3 days`，operator 可改）。冷静期只要 ≥ 最长保障期（**删掉 48h/72h 之后这个要求从 ≥72h 降到 ≥24h，好落地多了**），"看到橙色预警再买"的保单**整个保障窗都还没开始**，这场雨已经过去了。**这不是靠加价挡的，是结构上盖不住。**

> ⚠️ **必须说清版本**：`968` **演示链上 `coolingPeriod` 被设成了 `0`**（`04-脚本/rehearse-v2.js:228` 会把非 0 的值改掉，现场才能演示"买 → 喂价 → 判定 → 索赔"一条动线；这是 operator 可配开关，带 `CoolingPeriodSet` 事件）。**所以第 ① 条是"生产默认值"的性质，不是 968 这条演示链的性质。** 我们能站住的说法是：**合约已具备把冷静期设到 ≥ 保障期的能力，生产建议 ≥ 24h（`B端档位设计与不亏损证明.md` 四-D），演示链为了动线连贯设 0。** 反过来说，**只靠 ① 不够，真正让这一档不值得做的是 ② 和 ③。**

**② 这个维度不可核验。** "我是在预警期内买的"是买方自述，合约看不到。而任何能被自述的参数，一定会被选成对买方最便宜的那个 —— 给一个不可核验的维度定价等于没定价，只是给自己一个虚假的安全感。

**③ "哪种择时更强"随时段口径翻转，所以不该按"谁更强"挑加价对象。** 实测（见 `定价体系-v3-数表.md` §五）：

| | 加载倍数 |
|---|---|
| 临灾择时（前 24h 已累计 ≥25mm） | **5.50× ~ 17.15×** |
| 季节择时（只买雨季，**零预报能力**） | **4.13× ~ 12.53×** |
| 两者谁更强 | 本口径下临灾强 8/10 格、季节强 2/10 格 |

**注意这个结论会翻**：在旧的 72h 口径下是"季节 **37.52×** 碾压临灾 5.35~12.29×"，换成国标的 12h/24h 后变成"临灾略高，两者同量级（差 ≤2×）"。**一个随时段口径翻转的对比，不能用来决定给谁加价** —— 这恰恰是 ③ 的结论。

所以正确的应对是：把预算花在**身份绑定 + 冷静期**上（这两条同时压制季节择时和短期择时），而不是给一个不可核验、且量级不稳定的维度设一档价。κ 之所以仍然可以定价，是因为它挂在**可观测的销售渠道**（平台整批 vs 自助）上，不是买方自述的时点。

临灾条件率仍然逐格算出并存档，但**只作为诊断量，不进入任何报价**。

## 11. 诚实边界（写进对外材料时必须带）

1. **κ 与所有概率都是历史频率，不含预报技能。** 真实买家能拿到的信息比这更多，所以本表是最保守的一侧。
2. **月聚类块自举的块长固定为 1 个日历月**，与真实风险记忆尺度不同，只做参数不确定性的一阶修正。
3. **本表未含冷静期造成的生效延迟**。合约默认 3 天 ≥ 最长保障期 24h，意味着任何"临时追保"都盖不住当次天气 —— 方向上让本表更保守。
4. **`JUDGE_GAS` / `PAYOUT_GAS` 是 Sepolia 2026-10-06 的真链实测值**，主网 gas 价格不同则需重算。
5. **κ 的四个取值是设计参数，不是拟合结果。** 它们表达的是产品约束（有没有身份绑定、有没有冷静期、是不是平台整批发起），不是从数据里回归出来的系数。数据只用来算"给定 κ 下的期望赔付"。
6. **本表只覆盖 12h 与 24h 两个窗口，因为国标只有这两个。** 任何"48h/72h 的 12h/24h 等价档线"都只能是外推，本设计不外推。
7. **不构成精算意见。** 这是赛事原型，未做偿付能力评估、未考虑巨灾相关性、未做再保险安排。
