> **B → A ｜ 2026-10-07**｜归 B（`10-金融与定价/`）。本文是**完善方案**，不是赛期改动请求。
> 赛期合约状态不变：**A 已回执 v2 冻结**（`02-作战与答辩/v3-定价-A回B-2026-10-07.md`）。

## 0. 一句话

按国标 **GB/T 28592—2012《降水量等级》** 把 v3 的保障时长从 v2 的 **24 / 48 / 72h** 收成 **12h / 24h**，
档线从 `50 × h/24` 的**线性外推**改成**查国标表**，赔付档从 3 档收成 2 档 ——
**格数 60 → 40，批量带 180 → 120**，引擎 / 参考合约 / 全部对外材料同步重建完毕。

## 1. 为什么要删 48h / 72h（三条，都可复算）

**① 国标里没有这两档。** GB/T 28592—2012 §3 原文：

> 「降雨量按 **12 h，24 h 两个时间段**进行划分」

表 1「不同时段的降雨量等级划分表」（单位 mm）：

| 等级 | 12 h 降雨量 | 24 h 降雨量 |
|---|---|---|
| 微量降雨（零星小雨） | <0.1 | <0.1 |
| 小雨 | 0.1~4.9 | 0.1~9.9 |
| 中雨 | 5.0~14.9 | 10.0~24.9 |
| 大雨 | 15.0~29.9 | 25.0~49.9 |
| **暴雨** | **30.0~69.9** | **50.0~99.9** |
| **大暴雨** | **70.0~139.9** | **100.0~249.9** |
| **特大暴雨** | **≥140.0** | **≥250.0** |

**② 线性外推被国标自己的两列证伪。** v2 的 `thresholdOf(hours_) = 50 × hours_ / 24` 等价于
「降雨深度 ∝ 历时」的 `k = 1`，而国标自身 24h ÷ 12h 的比值是 **1.667 / 1.429 / 1.786 —— 没有一个是 2**。
DDF 的真实标度是次线性的（`k ≈ 0.5~0.7`），所以「国标 72h 暴雨线 150mm」这句话**不成立**。

**③ 实测更直接：72h 是「更贵、更难赔」的一档。** 五城 11 年逐小时滚动窗口（整数十分位口径）：

| 时长 | 档 0 触发率区间 | 说明 |
|---|---|---|
| 12h | 0.4273%~1.2954% | 武汉 0.8504 / 上海 0.7716 / 北京 0.4273 / 广州 1.2954 / 成都 0.6264 |
| 24h | 0.4377%~1.4200% | 武汉 0.7624 / 上海 0.7541 / 北京 0.4377 / 广州 1.4200 / 成都 0.5943 |
| 48h | 0.1899%~0.7750% | |
| **72h** | **0.1090%~0.5625%** | 武汉 0.2117 —— **只有 12h 的约 1/4** |

按 v2 的 15 格表，武汉 72h 保费是 12h 口径的约 4 倍，但**中奖率只有 1/4**。
**买家多付 4 倍保费、换到更低的赔付概率** —— 这不是保障，是反着的。

## 3. 要 A 侧知道的五件事（都不改赛期合约）

1. **`hours` 合法集合 `{24,48,72}` → `{12,24}`**：`hoursAllowed`、`MIN_HOURS`/`MAX_HOURS`、
   `04-脚本/` 里按 24/48/72 循环的喂价与建单脚本、`05-演示站点/` 的时长选择器（三选项 → 两选项）。
   若生产侧要保留 V3 落地后的映射接口，见 `v3-合约规格.md` §1.3。
2. **`TIER_BPS` 三档 → 两档**，`thresholdOf` 的线性外推作废、改查国标表（`v3-合约规格.md` §1.4）。
   这同时解决了 v2 的一处「虚假承诺」：`250 × h/24` mm（72h 即 **750mm**）在五城 11 年里**零触发**，
   国标 24h 特大暴雨线 `≥250mm` 同样零触发 —— 所以我们**不卖第三档**。
3. **`MIN_PREMIUM` / `premiumOf` 五点照旧**：`v3-合约规格.md` §7 里 A 已回执的三点（MIN_PREMIUM 不改、
   `premiumOf` 不改、`setPremiumGrid`/`setUnderwriting` 不弃）**不变**，本轮新增的两点（`hours` 集合、`TIER_BPS` 档数）
   与那三点一并**标注为「赛期不动」**。
4. **✅ 已闭环：`07-测试工具/check-v3-prices.js` 的「读回对的到底是哪份表」** —— 原脚本按**旧 60 格规格**
   折叠 `pricing-engine.json` 的 bands 并逐项读链上 480 项；引擎改成 40 格 / 120 行之后，它折叠出来的
   行数是 40 × 6 = 240 项的量级，**再跑必然对不上**。
   **B 侧实测（2026-10-07 17:48，B 已对齐 `80ea897`）**：`--offline` → `payload：40 行（40 可售 / 0 不卖）`、
   `payload 自身不变量 ✅`，这一半是好的；但去掉 `--offline` 真读 968 → **`读回比对：320 项，❌ 262 项不符`（exit 1）**，
   例如 `chengdu 24h t1c0 链上 750000000000000 vs 表 700000000000000`。
   **不是脚本的 bug，是链上还是旧口径**：968 那个合约存的是上一轮 60 格 / 24-48-72 的价，本地表已是国标 40 格 / 12-24。
   **A 的处置（`4547f5cc`，B 复核通过）**：把「对照表」与「设计表」分开 —— 新增
   `07-测试工具/fixtures/pricing-engine-deployed-968.json`（= 部署当时那份 JSON，取自提交 `7e05c6c^`，
   60 行 / 180 带 / 时长 24·48·72），脚本默认拿它真读 968 比对 **480 项 ✅**，`--spec=` 可换表（指向设计层那份
   时**对不上是预期的**，只用于看差异）；新表的自证归 `10-金融与定价/ref/verify_pricing_v3.js`（687 项）。
   **这条比 B 原本建议的两条出路都好**：既保住了「真读链」的价值，又不让脚本因为设计层演进变红。
   B 侧只需把对外口径从「同一个脚本读链会 262/320 不符」改回「拿冻结对照表真读 968 比对 480 项相符 +
   40 格表由参考合约自证 687 项」（已改）。
5. **`02-作战与答辩/决策记录.md:30` 里有一批过时数字**（A 的地盘，B 不动）：

## 4. 对外口径的增量（在 A 定的统一口径上补两句）

A 定的口径是：「链上**现在**执行的是**地区 × 时长 15 格定价 + AI 承保加价**
（`premiumOf(regionId, hours)` 逐格读回可验）；骑手类型 / 渠道 / 批量是 v3，已算好并核验、赛期不动合约。」

本轮要补的两句：

> **① 时长**：「v2 链上卖的是 24 / 48 / 72 三档，其中 **48h / 72h 是 `50 × h/24` 的线性外推、国标里没有这两档**；
> v3 收回国标的 **12h / 24h**，档线直接取国标表 1 的暴雨 / 大暴雨下限。」
> **② 档数**：「v2 的第 3 档（`250 × h/24`，72h 即 750mm）在五城 11 年里**一次都没触发过** ——
> 写在合约里但永远赔不到的条款，是我们主动承认的虚假承诺；v3 只卖国标的前两档。」

**两条禁语**：❌「国标 48h / 72h 档」（国标没有）；❌「v3 也是 24/48/72 三档」（v3 是 12h/24h）。
